# Roadmap

The goal for the first week: take a typical .NET Framework 4.8 solution (an ASP.NET MVC / Web API app plus the class libraries it uses) and move it to .NET 10 step by step, with the user approving each change or letting the tool run unattended.

## Next up, in priority order

Driven by a real migration: several .NET Framework 4.8 repositories, shared libraries published to a private NuGet feed, apps that consume them, and data (password hashes, serialized objects) that must stay byte-for-byte compatible. Work goes top to bottom; the web project items (P20, 0.5.3 onwards) wait behind P5–P19.

| # | Item | Why it comes here |
|---|---|---|
| P1 ✅ | **Data-compatibility analysis.** Findings, with what to verify, for code whose output silently changes between .NET Framework and modern .NET: `Encoding.Default` / `GetEncoding(0)` (the ANSI code page on .NET Framework, always UTF-8 on modern .NET), code-page encodings used without registering `CodePagesEncodingProvider`, `Encoding.UTF8.GetString` over binary data such as hashes (ill-formed UTF-8 is replaced differently since .NET Core 3.0), culture-sensitive `ToLower()`/`ToUpper()` (Turkish İ/ı), `GetHashCode()` results that are stored or sent, and compressed output compared byte for byte | Hashes and stored data that change without an error are the most expensive migration bug; this has to be known before any code moves |
| P2 ✅ | **Central Package Management.** Generate `Directory.Packages.props` from every `PackageReference`, report version conflicts, remove the `Version` attributes, set `ManagePackageVersionsCentrally` | Wanted in every repository before the move, and it makes P3 easier |
| P3 ✅ | **File references → packages.** `HintPath` DLLs outside `packages/` (for example a `SolutionItems` folder) become `PackageReference`s, mapped by a small mapping file or by assembly name; hard-coded package versions (such as a fixed `1.0.0`) are reported | Shared libraries must come from the feed, not from copied DLLs |
| P4 ✅ | **Cleanup steps.** ✅ `dotnet-lift cleanup`: remove references nothing uses (checked with Roslyn: leftover System.Web.Mvc, System.Web.Optimization, Owin, System.EnterpriseServices, Unity) and the `MigrationBackup` / `_UpgradeReport_Files` folders left by Visual Studio. ✅ `analyze` reports the same unused references as info findings (same check, nothing changed). ✅ `cleanup --remove-project <name>`: remove a project from the .sln after listing what depends on it (project references, file references to its DLL, indirect dependents); refused while anything references it | Everything removed is something that does not have to be migrated |
| P5 ✅ | **Test projects.** ✅ `analyze` recognises MSTest / xUnit / NUnit projects (packages, references, test project type GUID), lists the packages `dotnet test` needs and which are missing, and warns about MSTest v1 (Visual Studio reference), NUnit 2 and xUnit 1. ✅ The SDK-style conversion adds the test SDK and the adapter that `dotnet test` needs (adapter version matched to the framework, versions in `Directory.Packages.props` under CPM) and replaces MSTest v1's Visual Studio reference with MSTest.TestFramework + MSTest.TestAdapter 3.x; NUnit 2 / xUnit 1 are left for the user to update first. ✅ `upgrade` runs `dotnet test` for the new target once a test project builds, and lists failing tests by name | Tests have to survive the upgrade and prove it |
| P6 🚧 | **Migration profile (`dotnet-lift.json`).** ✅ `dotnet-lift init` writes it; `target`, `multiTarget` (auto / always / never, per-project with `*` wildcards) and `commits` (step / single) are read by `analyze` and `upgrade`; `codePage` is used by P9. ✅ `binaryFormatter` (json / compatibility, also per project) is used by P8. ⏳ The remaining rewrite targets (cache type, request-context interfaces) arrive with P13 and P14. One file per repository with the team's decisions: single target (`net10.0` only, consumers stay on the last .NET Framework package) or multi-target, per-project exceptions; commits per step or one conversion commit; and the targets of the rewrites below (code page, BinaryFormatter strategy, cache type, request-context interfaces) | Without it the tool's defaults contradict real team decisions; everything below reads it |
| P7 ✅ | **Test-first workflow and golden vectors.** ✅ `dotnet-lift add-tests --project <name>` scaffolds `<name>.Tests` (MSTest, with a first test that loads the library) next to the library and adds it to the .sln (the library's configurations and solution folder); it targets what the library targets (`net48` today, `net48;net10.0` once it multi-targets), so `upgrade` retargets it right after the library and the same tests run on both; package versions come from `Directory.Packages.props` or the solution's other MSTest projects. ✅ The scaffold adds `GoldenVector.Check(name, string | byte[])`: recorded into golden/ on .NET Framework, compared byte for byte on modern .NET (missing there = failure), with the first differing byte, hex and escaped text in the message; `DOTNET_LIFT_GOLDEN=record` re-records. CI records on net48, upgrades, and sees `upgrade` report the changed hash on net10.0 | Almost every migration task ends with "the same tests pass on the new framework" |
| P8 ✅ | **BinaryFormatter: compatibility-package path.** For persisted data: reference the unsupported `System.Runtime.Serialization.Formatters` package and set the AppContext switch instead of changing the format; the System.Text.Json rewrite stays for caches. Chosen in the profile. ✅ `"binaryFormatter": "compatibility"` (top level or per project) plans a "Keep BinaryFormatter with the compatibility package" step instead of the JSON rewrite: the package for the modern target only, `EnableUnsafeBinaryFormatterSerialization` and `NoWarn SYSLIB0011` in the project file, code untouched, no explicit approval needed (the format does not change). The step names the projects that use the library, because the switch is read from the application's own runtimeconfig. CI writes data with the upgraded library on net48 and reads it back on net10.0 | Stored data must stay readable until a planned data migration |
| P9 ✅ | **Explicit code pages.** Rewrite `Encoding.Default` / `GetEncoding(0)` to the code page set in the profile (e.g. 1254) and register `CodePagesEncodingProvider` once | Removes the most common cause of hashes that change silently |
| P10 ✅ | **Microsoft.Data.SqlClient.** `System.Data.SqlClient` → `Microsoft.Data.SqlClient` (namespaces, package) with a warning about the `Encrypt=true` default. ✅ `analyze` finds usages (Roslyn), the old package, connection strings without `Encrypt`, `DbProviderFactories.GetFactory("System.Data.SqlClient")` and the EF 6 provider; the `sqlclient` step rewrites namespaces, swaps the package (CPM-aware) before the retarget, and needs explicit approval unless `"sqlClient": "microsoft"` is in the profile (`keep` skips it) | Needed by most data-access libraries |
| P11 ✅ | **More analysis rules.** RealProxy, CallContext, custom ConfigurationSection classes, ServicePointManager, JavaScriptSerializer, COM references, MarshalByRefObject, Enterprise Library, `#if NET6_0`-style symbols, Windows-only APIs (for Linux hosting), Razor template engines, System.Drawing usage inventory with counts. ✅ Line rules in the source scan (Removed / Obsolete API ones join the planned removed-apis task); COM references, Enterprise Library and the System.Drawing inventory are one finding per project | Cheap, and each one turns a surprise into a planned task |
| P12 ✅ | **Package upgrade advisor.** Packages that need a major upgrade on modern .NET (e.g. NEST, Quartz, StackExchange.Redis, Npgsql, Hangfire, MassTransit, MongoDB.Driver, SSH.NET, EF6, JwtBearer, Serilog), with the breaking changes to expect. ✅ Version-aware catalog of 28 packages (target + breaking changes); one agent-assisted `package-upgrades` task before the retarget, EF 6 stays in its own step | Package upgrades are a large share of the work and easy to underestimate |
| P13 ✅ | **Request context beyond the user.** Generalise the CurrentUser step: `HttpContext.Current` Items / Session / Request / User → interfaces named in the profile. ✅ `"requestContext"` maps user / items / session / request / response / server / cache (and `context` for null checks) to C# expressions; whole files only; plans `request-context` instead of `current-user` | Libraries that read the request in many files |
| P14 ✅ | **Configurable cache target.** `HttpRuntime.Cache` → `IMemoryCache` or a cache abstraction named in the profile, instead of only `MemoryCache.Default`. ✅ `"cache"` templates (get / set / setAbsolute / setSliding / remove with `{key}` `{value}` `{absolute}` `{sliding}`), validated on load | Teams usually already have a cache abstraction |
| P15 | **Exact-equivalent rewrites.** `FormsAuthentication.HashPasswordForStoringInConfigFile` → the same hex hash, `CallContext.LogicalGetData/SetData` → AsyncLocal, `#if NET6_0` → `NET6_0_OR_GREATER`, JavaScriptSerializer → System.Text.Json (with approval) | Mechanical changes that must keep output identical |
| P16 | **Security findings.** Exception messages returned to clients (`ex.Message` in a response), secrets in config files | Cheap to find, and migration reviews look for them anyway |
| P17 | **Binary dependency inventory.** Referenced DLLs that target only .NET Framework (read from the assembly itself), as a list of vendor SDKs to request | Vendors take a long time to answer |
| P18 | **WCF and ASMX clients.** Inventory of service references and web references, with the `dotnet-svcutil` command for each | Many integration libraries are mostly service clients |
| P19 | **Windows-only projects.** Detect WinForms / WPF / COM / Registry use and target `net10.0-windows` | Desktop agents and resolvers cannot target plain net10.0 |
| P20 | **Web project, keeping responses identical.** Newtonsoft.Json with Web API 2 behaviour; route inventory (old vs new, for completeness); a response-comparison tool (same request to old and new host, JSON/status/header diff); Global.asax → Program.cs; Web API 2 controllers → ASP.NET Core; HTTP handler and module inventory; then 0.5.3 → 0.6 below | The web host moves last and must answer exactly like the old one |
| later | 0.4 (prompt export for any AI assistant, MCP server mode) | Useful once the rule-based steps above are in place |

## Design principles

- **Works for everyone, with nothing but the .NET SDK.** No API key, account, paid service or network access is needed for any feature. AI help is always optional and always brought by the user.
- **Deterministic first.** Anything that can be done with rules (project files, packages, config) is done without an LLM. The agent is only used for code that needs understanding.
- **Every step is reviewable.** Each step is its own git commit, so it can be inspected or reverted.
- **Never leave the solution unbuildable for long.** Libraries multi-target `net48;net10.0` until the web app has moved.
- **No MSBuild dependency for analysis.** Legacy project files are read as XML so the analysis runs on macOS and Linux too.
